# Ollie — Phase 3 Implementation Plan (track record)

## Context

Phases 0–2 are complete: the pipeline proposes signals on schedule against the real Robinhood MCP, the owner decides them in the iOS app, and approved paper fills open track-record lots. What nothing does yet is *finish* a trade. The `track_record` table has carried `exit_price`, `realized_pnl`, and a `closed` status since Phase 0, and `appendTrackRecord` can write a closed row today — but no code path ever produces one. `unrealized_pnl` is written once at entry and never refreshed. The strategy already emits sell candidates (`rsi_overbought`, `macd_bearish_cross` in `technical.ts`), but a sell is a standalone signal with no relationship to any open lot, and in paper mode it cannot even survive the risk gate — `sell_without_position` checks *broker* positions, and the Agentic account is unfunded, so every paper sell dies there today.

Phase 3 closes the loop. **Exit (PRD §10): outcomes and PnL accrue per signal; the track record surfaces an equity curve, win rate, and average return; paper runs for a sustained period to build a record worth publishing.** PRD §9 is blunt about why this phase matters more than its line count: the credibility of this record *is* the product. Every choice below is made against that standard — nothing invented, nothing edited, every published number recomputable from append-only rows.

Phase 3 adds no new external dependency and no new service. It is: an additive migration, exit logic in the pipeline and executor, one new cron job, one new endpoint, one new app screen, and then weeks of letting it run.

## Decisions proposed here (owner should confirm before 3.1)

1. **The strategy's sell rules are the exit policy; an approved sell closes the open position.**
   The alternative — a separate stop-loss/take-profit engine watching intraday prices — is a second decision system with its own cadence, its own quote-polling machinery, and its own claim on determinism, bolted on before the first system has a record. The sell rules already exist, already fire on the same daily bars, and are already pure functions; what is missing is only the plumbing that (a) lets a paper sell through the risk gate and (b) matches its fill against open lots. A sell that fires with no open position is rejected by the risk gate exactly as today, just against the right position source. This does mean exits are as slow as the entry rules — a losing position waits for RSI to cross back above 70 or a MACD bearish cross — which is why decision 3 exists.

2. **Exits are owner-approved, through the identical pending → decide flow. Nothing acts autonomously.**
   The consistent choice is also the safe one: PRD §1 says "human approves every order," and autonomy is explicitly a Phase 5 flip gated on a lawyer and this very track record. An automatic exit would be the first thing in the system that moves (paper) money without a tap, and it would ship *before* the record that is supposed to justify autonomy exists. The cost is real: a missed 15-minute approval window on a crossing signal means the exit does not re-propose until the next cross, which can be weeks. Accepted, because (a) push notifications exist, (b) an expired exit signal is an honest, visible record of a missed decision, and (c) the time-stop below re-proposes daily and bounds the damage.

3. **A time-stop exit rule, `max_holding_period`, default 30 trading days, re-proposing daily until decided.**
   Without it, Phase 3 can complete its code and still fail its purpose: a sustained paper run in a trending market can end with zero closed trades and therefore no win rate, no average return, and nothing worth publishing. The rule is deterministic — a pure function of open lots plus bars: if a lot has been open ≥ `MAX_HOLDING_DAYS` bars, propose a sell of the full position. Because the condition stays true on every subsequent bar and the dedupe key includes `barTime`, a missed approval re-proposes tomorrow, unlike the crossing rules. This is deliberate purity drift worth confirming: the entry decision remains a function of OHLCV alone, but this exit decision takes position state as an input. It is still replayable — same lots plus same bars give the same answer — but "decisions are pure functions over OHLCV" becomes "over OHLCV and the (append-only) position record" for exits. `MAX_HOLDING_DAYS=0` disables it.

4. **Exits close the whole position, oldest lots first. No partial exits.**
   Entry sizing is one notional unit and the position cap is 2× notional, so a position is at most a couple of lots; partial-exit bookkeeping (a `remaining_quantity` concept, mid-lot splits, per-slice PnL) buys nothing at this scale and complicates the one thing that must stay simple — one closed row per entry lot, `realized_pnl = (exit − entry) × quantity`. FIFO ordering earns its place in exactly one race: a buy on the same symbol approved *after* the exit was proposed. The exit's quantity was fixed at proposal time, so the executor closes oldest lots first until that quantity is consumed and the newer lot stays open. If nothing remains to close (another exit won), the approval is refused with `409` *before* the status transition — same pre-flight doctrine as 2.2, so the signal stays pending and decidable rather than stranded approved-but-unfilled.

5. **Mark-to-market is a daily post-close cron job writing one mark row per open lot; a missing quote is a gap, never a guess.**
   Two different consumers need `unrealized_pnl` and they need different things. The dashboard needs *now* and already computes it live from quotes at read time — that stays untouched. The track record needs *history*: an equity curve requires knowing what open positions were worth on each past day, and no read-time computation can recover that later. So a `MARK_CRON` job (default `15 16 * * 1-5`, ET, after close) appends one row per open lot: status `open`, `unrealized_pnl` against the quote, and a new `mark_price` column so the row is auditable rather than a bare number. Daily and not faster because the strategy trades daily bars and the curve is daily; more marks are append-only bloat with no analytical value. If a symbol's quote is unavailable, no row is written and the gap is logged — the dashboard's rule that a partial number is worse than an admitted absence applies with more force to rows that can never be deleted. One mark per lot per trading day, enforced by checking for an existing same-day mark before appending, so a restart or manual run cannot double-mark.

   **Amended 2026-08-13 — the kill-switch exemption below was rejected.** This job halts with both halves of the switch like every other. The exemption's argument (marking observes, it does not act; a halt leaves a permanent hole in the curve) lost to a simpler one: these rows are permanent and uneditable, and an incident is precisely when you least want them accruing. The curve gap is real and is the point — it records that the switch was thrown.

6. **The equity curve is computed at read time from the rows, never stored.**
   A stored curve is a second copy of the truth that can drift from the rows it summarizes, and drift in published performance is the one failure this product cannot survive. Computing from rows means anyone — including a Phase 4 subscriber — can recompute the curve from the append-only record and get the same answer, which is the entire credibility argument. Cost is trivial: the caps allow 3 signals/day, so a year of running is hundreds of rows, and the whole computation is one table scan. A consequence worth stating plainly: when a correction row lands, derived views change — and they change *at the correction's date*, not retroactively. The curve shows when the record knew something, because rewriting the past shape of a published curve is exactly what append-only forbids. The curve is a **PnL curve based at zero, not a portfolio NAV** — there is no cash ledger and paper mode has no real cash, so a NAV would be an invented denominator.

7. **The production track record starts from a declared clean slate.**
   The Railway database holds smoke-test signals from 1.7 and 2.x verification, and the triggers correctly refuse to delete them. Before 3.8 begins, the owner either `TRUNCATE`s all signal/execution/track-record tables (the one legitimate use of superuser access, done once, before the record exists) or the published record declares an epoch timestamp and every aggregate filters to rows after it. Truncation is cleaner and proposed; it must happen before the first counted run, because afterwards it would be editing the record.

## Definitions (these become code and contract text verbatim)

- **A trade** is one entry lot, open to close: the latest track-record row per entry signal, when that row is `closed`. Latest-row-per-signal is the established convention (`listOpenLots`), and it is what makes corrections work — a correction row supersedes, never double-counts.
- **Realized PnL per trade** = `(exit_price − entry_price) × quantity`. Long-only, so no sign gymnastics. Fill prices already embed 10 bps slippage against the trader on *both* legs, so paper results understate rather than flatter (PRD §11); Robinhood charges no equity commission, so fees are zero and the contract says so rather than staying silent.
- **Per-trade return** = `realized_pnl / (entry_price × quantity)`.
- **Win** = `realized_pnl > 0`, strictly. A scratch trade is not a win; counting ties inflates the headline number.
- **Win rate** = wins ÷ closed trades. **Open positions are excluded from the denominator** — an open trade has no outcome yet and guessing one corrupts the statistic in whichever direction the guesser prefers. The open-position count is reported alongside so the exclusion is visible, not hidden. With zero closed trades, win rate is `null`, not `0` — the same honesty convention as the withheld dashboard totals.
- **Average return** = unweighted arithmetic mean of per-trade returns over closed trades. Unweighted because entries are sized to a fixed notional anyway, and because it matches how a subscriber acting on each signal with fixed size experiences the record.
- **Equity curve point** for trading day *d* = (cumulative realized PnL from closed rows with `recorded_at` ≤ end of *d*) + (sum of `unrealized_pnl` over that day's mark rows). If any lot open on *d* lacks a mark for *d*, the point is withheld — a partial sum understates or overstates the curve, same rule as the dashboard totals, and the API says which days were withheld.

## Database changes

One additive migration. No new tables, no trigger changes — the append-only triggers on `track_record` already cover the new columns because they reject every UPDATE and DELETE regardless of column.

```sql
ALTER TABLE track_record
  ADD COLUMN closed_by_signal_id uuid REFERENCES signals(id),  -- the exit signal that closed this lot
  ADD COLUMN mark_price numeric(18,6);                          -- the quote a mark row used
```

Both nullable: entry rows have neither, mark rows have `mark_price`, close rows have `closed_by_signal_id`. `closed_by_signal_id` is what makes the record legible — a closed row names the exit signal that caused it, so the full story of any trade (entry signal → fills → marks → exit signal → close) is walkable from the rows alone. Row kind is derivable (`status` + which nullable columns are set), so no `kind` enum; if queries get awkward the enum can be added later without touching existing rows.

Config additions to `.env.example`: `MARK_CRON=15 16 * * 1-5`, `MAX_HOLDING_DAYS=30`.

## API contract (summary — `docs/openapi.yaml` regenerated from the zod schemas as always)

- **`GET /v1/track-record`** — new. Everything the PRD §4.4 surface needs, one call:
  - `stats`: `closed_trades`, `open_positions`, `wins`, `losses`, `win_rate` (nullable), `average_return` (nullable), `realized_pnl_total`. Decimal strings, two places for computed aggregates, per the documented convention.
  - `equity_curve`: array of `{date, realized_cumulative, unrealized, equity}` points, plus `withheld_dates` naming days a missing mark suppressed.
  - `trades`: closed trades — `signal_id`, `symbol`, `quantity`, `entry_price`, `exit_price`, `realized_pnl`, `return`, `opened_at`, `closed_at`, `closed_by_signal_id`. The volume is small enough that pagination would be ceremony; a `limit` param exists for the day it is not.
  - This payload is deliberately the shape Phase 4's subscriber MCP server will re-expose. Building it here means Phase 4 publishes an existing, tested aggregate rather than inventing one under launch pressure.
- **`GET /v1/dashboard`** — `totals.realized_pnl` becomes real: the sum of `realized_pnl` over latest-per-signal closed rows. The "zero until Phase 3" description in the schema is replaced; the response shape is unchanged, so the Swift client recompiles without edits.
- **`POST /v1/signals/{id}/decision`** — behavior change on approving a sell, documented in the description: the response's `execution` is the exit fill, and a new `409` variant `no_open_position` covers approving an exit whose position was already closed by a racing exit. The signal stays pending in that case.

## Pipeline and executor changes

**Paper position source (the gap that blocks everything else).** The risk gate's sellable-shares map and the pipeline's pending-exposure computation currently read `broker.getPositions()` — real account state, which is empty and always will be in paper mode. Phase 3 introduces one seam: in paper mode, position state for the risk gate comes from `listOpenLots` (per-symbol summed quantities); in live mode (Phase 5) it stays the broker. This is account bookkeeping feeding a gate, exactly the category `technical.ts`'s header already assigns to position awareness — the pure decision functions do not change. While in there, pending *sell* signals stop counting toward pending exposure: a committed exit reduces exposure, and counting it as an increase makes the exposure cap reject entries it should not.

**Exit sizing.** `evaluateTechnical` sizes every candidate by notional today, including sells — and `quantity_rounds_to_zero` suppresses a sell whenever one share costs more than `ORDER_NOTIONAL_CENTS`, which is nonsense for an exit (the position exists; its size is the position's size). Sell candidates stop being notional-sized: the pure function emits the sell with the rule and indicators, and the pipeline sets its quantity to the symbol's total open paper shares before the review snapshot, so the snapshot and the eventual fill describe the actual exit. A sell whose symbol has no open lots never reaches sizing — the risk gate rejected it.

**The time-stop.** New pure function `evaluateExits(openLots, candles, cfg)` in `strategy/exits.ts`: for each symbol with an open position, if the oldest open lot has been open ≥ `MAX_HOLDING_DAYS` *bars* (trading days, counted from the candle series, not calendar days), emit a sell candidate for the full position with rule `max_holding_period`. Runs in the pipeline after the crossing rules; dedupe key `max_holding_period:{symbol}:sell:{barTime}` gives one proposal per bar and daily re-proposal for free.

**Exit execution.** `PaperExecutor` branches on side. A buy is unchanged. A sell: compute the fill (estimate minus slippage, as today), record the execution row, then — in one transaction — re-read the symbol's open lots and append one closed row per lot, oldest first, until the signal's quantity is consumed: `exit_price` = fill, `realized_pnl` = `(fill − entry) × lot quantity`, `closed_by_signal_id` = the sell signal. The sell signal itself opens no lot — the current behavior of a sell fill opening its own phantom row is exactly what this milestone deletes. Zero lots remaining at execution time throws before any write; the decision route's pre-flight catches the common case first so the transition is never consumed. Lot boundaries align by construction (the quantity was the sum of whole lots at proposal, and lots can only be *added* afterwards); if they somehow do not, the executor refuses loudly rather than writing a partial-lot row.

**The mark job.** Third croner job beside pipeline and expiry, `protect: true`, same ET timezone: fetch quotes for open-lot symbols, and for each lot without a mark row today, append `{status: 'open', unrealized_pnl, mark_price, recordedAt}`. Kill switch does *not* gate marking — the switch halts proposals and execution, but recording what existing positions are worth is observation, not action, and a curve with a hole in it because the owner hit the brakes would misrepresent the record.

## Risks / open questions

1. **Closed-trade volume is market-dependent and cannot be promised.** Twenty trading days might close two trades or ten. The time-stop bounds the worst case (nothing can stay open past 30 bars un-proposed), but a thin record at the end of 3.8 means extending the run, not shipping Phase 4 early. The exit criterion deliberately requires only one closed trade; "worth publishing" is the owner's judgment call at the end, and this plan does not pretend a number decides it.
2. **The mark price is a 16:15 ET last-trade quote, which can be an after-hours print** rather than the official close. Recorded verbatim in `mark_price`, so the record is auditable even where it is imperfect; switching the source to the official daily close from historicals is a contained change to the mark job if the drift proves visible. Not solved now because the official close for "today" is itself unstable until the bar is final.
3. **Decision 3 is purity drift and needs explicit sign-off:** exit decisions consume position state. Replayability survives (the position record is append-only, so the inputs at any past moment are reconstructible), but the one-line version of the determinism story gets a clause longer.
4. **A missed exit approval can hold a position for weeks** when only a crossing rule covers it. Mitigated by push and the daily re-proposing time-stop, but between a bearish cross and the time-stop floor there is a window where the record honestly shows a strategy that held longer than it signaled. That is the record doing its job, not a defect — but the owner should expect to see it.
5. **Corrections reshape derived views at the correction date.** Correct by design, but when Phase 4 exposes the curve to subscribers, a visible change needs an explanation surface — likely "the rows are public, recompute them." Deferred to Phase 4 with the subscriber contract.
6. **The truncation in 3.8 is irreversible and must be the last one ever.** After the sustained run starts, there is no clean-slate button — that is the point. The owner should treat the pre-run checklist (env values, push working, one forced round trip) as the final rehearsal, because everything after it is on the record.
7. ~~**Kill-switch-exempt marking is a deliberate exception**~~ — **withdrawn 2026-08-13.** The mark job halts with the switch like everything else, so there is no exception to explain in the Controls copy and no first crack in "the switch means stop". The cost is a permanent gap in the curve for any halted day, which is the honest record of a halt rather than a defect.

8. **The immutability triggers do not stop `TRUNCATE`, and that is the whole guarantee's blind spot.** Verified 2026-08-13: the Phase 0 triggers are row-level and fire on `UPDATE` and `DELETE`, but `TRUNCATE` is a statement-level operation that bypasses them entirely. `test/helpers/db.ts` truncates all five tables before every test run and succeeds, which is the proof — the same statement decision 7 relies on for the clean slate would work just as well the day after the record starts.

   This matters more than an ordinary gap because the append-only record *is* the product (PRD §9): "the credibility is the product." A record that cannot be edited but can be silently erased in one statement is a weaker claim than the docs currently make, and a subscriber who understood the distinction would be right to discount it.

   **Closed on 2026-08-13**, ahead of the epoch rather than after it: the `reject_truncate` migration adds a `BEFORE TRUNCATE` trigger on `signals`, `executions`, `signal_events`, and `track_record` that raises unconditionally, plus a test asserting `TRUNCATE` now fails. The test helper keeps working by dropping the guard inside its transaction, or by moving test resets to a schema that never carries it — deciding which is part of the work, not a detail to wave at. Until then, "immutable" should be read as "immutable against edits, trusted against erasure," and Phase 4's subscriber-facing claims should not overstate it.
