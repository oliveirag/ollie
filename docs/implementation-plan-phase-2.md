# Ollie — Phase 2 Implementation Plan (owner iOS app + owner API)

## Context

Phases 0–1 are complete: the orchestrator generates signals on schedule, persists them immutably with review snapshots, and the owner approves or rejects through `scripts/decide-signal.ts`. Phase 2 replaces that CLI with the thing the PRD actually promises — a SwiftUI app where the owner decides with one tap, sees positions and PnL, and can hit a kill switch. **Exit (PRD §10): the owner approves or rejects real proposals on their phone; the CLI is no longer the daily surface.**

Phase 2 does not touch signal generation. The pipeline, strategy, risk gate, and executor are done; this phase builds the *decision surface* over the repository functions that already exist. `transitionSignal`, `getAppSettings`, `setKillSwitch`, `listPendingSignals` — the API is largely a thin, authenticated HTTP skin over calls the CLI already makes.

Dependency on 1.7: none for most of the phase. Everything through milestone 2.6 runs against the mock broker locally. The final end-to-end (2.7) wants the Railway deploy and real credentials from 1.7, but the two tracks can proceed in parallel.

## Decisions proposed here (owner should confirm before 2.1)

1. **Defer Sign in with Apple to Phase 4; use a pre-shared owner token for Phase 2.**
   This is deliberate drift from PRD §5, so it needs sign-off. SIWA solves stranger onboarding, and Phase 2 has exactly one user, already known. Standing up SIWA now means solving owner-binding ("whoever signs in first is owner" is a footgun; pinning an `apple_user_id` in env is ceremony with no second user to keep out) and building the `users` table a phase before anything reads it. Instead: a long random `OWNER_API_TOKEN` generated at deploy, stored in the iOS Keychain on first launch, sent as a bearer header. TLS via Railway. SIWA arrives in Phase 4 with the `users` table, where it earns its place — subscribers are strangers.

2. **Fastify for the API, with zod schemas as the validation layer.**
   The current server is raw `node:http` serving one route. That was right for a health check and wrong for a real API. Fastify + `fastify-type-provider-zod` keeps zod as the single validation idiom (it already guards env and MCP responses), and `@fastify/swagger` can emit an OpenAPI document from the same schemas. `/healthz` moves onto Fastify unchanged.

3. **`docs/openapi.yaml` stays the source of truth, enforced by a drift test.**
   The PRD makes the YAML the cross-language contract. Rather than hand-maintaining it and hoping, a vitest test renders the Fastify-emitted spec and diffs it against the checked-in file — drift fails CI, and the fix is always "update the contract first."

4. **Swift client generated by `swift-openapi-generator`** (Apple's, SPM build plugin). The client is build product, not checked-in code.

5. **Xcode project generated by XcodeGen** (`project.yml` checked in, `.xcodeproj` generated). A declarative project file is the difference between an agent being able to add a source file and it hand-editing pbxproj UUIDs.

6. **APNs hand-rolled over `node:http2`, token-based `.p8` auth.**
   Node's `fetch` speaks HTTP/1.1 only and APNs requires HTTP/2. The mainstream `node-apn` package is in the same state the `technicalindicators` package was in Phase 1 — aging, and we rejected that one for it. The whole client is ~100 LOC: mint an ES256 JWT with `node:crypto`, POST over an `http2` session, handle the documented status codes. No new dependency.

7. **No approve-from-lock-screen in v1.** Actionable notification buttons that move (paper) money without unlocking the phone are a misfeature at this stage. Tap opens the app; the app decides. Revisit with `authenticationRequired` actions later if the friction proves real.

`decide-signal.ts` is **not deleted**. It talks to the repository directly, not through the API, which makes it the break-glass path when the phone is dead or the API is down — same tier as flipping the kill switch in psql. It leaves daily use, not the repo.

## API contract (summary — `docs/openapi.yaml` is normative)

All routes under `/v1` require `Authorization: Bearer <OWNER_API_TOKEN>`; a missing or wrong token is `401` with no body detail. `/healthz` stays public.

- **`GET /v1/signals?status=pending|decided`** — list. Pending items include `expires_at`, computed at read time as `created_at + SIGNAL_EXPIRY_MINUTES`. The expiry sweep remains the authority; the timestamp is for the countdown UI, not a promise.
- **`GET /v1/signals/{id}`** — full detail: thesis (+ `thesis_source`), indicators, review snapshot (estimated price, alerts), status history from `signal_events`.
- **`POST /v1/signals/{id}/decision`** — body `{ "action": "approve" | "reject", "reason"?: string }`.
  - Approve runs the executor for the signal's own mode synchronously; the response carries the fill (`fill_price`, `filled_at`). Paper never touches the broker.
  - The signal left `pending` already (decided, expired, raced by the sweep) → `409` with the current status. `SignalNotPendingError` already guarantees exactly-once at the DB tier; the API just translates it.
  - Approve on a live-mode signal → `409` surfacing `LiveModeNotEnabledError` until Phase 5.
- **`GET /v1/dashboard`** — open lots (latest `track_record` row per signal, status `open`), each with entry price, quantity, current quote, unrealized PnL; totals across lots. Quotes are best-effort: broker unreachable → lots still return with `quote: null` and the app shows entry-basis only. **Realized PnL reads as zero until Phase 3** — nothing closes positions yet, and the dashboard reports the truth rather than inventing it. A sell fill currently *opens* a row; matching it against the buy lot is explicitly Phase 3's job, and this endpoint must not pre-empt it.
- **`GET /v1/settings`** — `kill_switch`, `execution_mode`, plus `live_trading_enabled` (env, read-only) so the app can render the live toggle as locked.
- **`PUT /v1/settings`** — body `{ "kill_switch"?: bool, "execution_mode"?: "paper" | "live" }`. Setting `execution_mode: "live"` while `LIVE_TRADING_ENABLED` is false → `409`. The API edge mirrors the executor's double gate; the toggle exists, visibly locked, exactly as PRD §4.3 wants.
- **`POST /v1/devices`** — body `{ "apns_token": string, "environment": "sandbox" | "production" }`. Upserts; tokens rotate.

## Database changes

One table. `users`/`subscriptions` stay deferred to Phase 4 with the auth decision.

```sql
CREATE TABLE devices (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  apns_token   text NOT NULL UNIQUE,
  environment  text NOT NULL DEFAULT 'production',   -- 'sandbox' | 'production'
  created_at   timestamptz NOT NULL DEFAULT now(),
  last_seen_at timestamptz NOT NULL DEFAULT now()
);
```

Plain mutable table — a device token is operational state, not part of the record. No triggers. Rows whose token APNs reports as `410 Unregistered` are deleted by the dispatcher.

## Push

- **Trigger:** pipeline stage 8 already logs "signal persisted"; the same seam calls `notifyNewSignal(signal)`. Push failure is logged and swallowed — **push must never block or fail a signal**, same doctrine as the thesis.
- **Payload:** id, symbol, side, quantity, estimated price, `expires_at`. Nothing from the raw review snapshot. `interruption-level: time-sensitive` (a 15-minute expiry justifies it; requires the entitlement).
- **Delivery is best-effort and the app must not depend on it.** The approvals list refetches on foreground and on pull-to-refresh; a missed push costs the owner one expired signal, visible with its reason in the decided list — annoying, never silent.
- **Secrets:** `APNS_KEY_P8` (base64), `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID` — Railway variables, same tier as the broker credential.

## iOS app

Swift 5.10+, SwiftUI, iOS 17+, `@Observable` MVVM, URLSession async/await. Layout per PRD §7 (`ios/` beside `backend/`), `Features/Subscriber/` not scaffolded until Phase 4.

Screens, in build order:

1. **Approvals** — pending list with countdowns; detail showing symbol/side/quantity, estimated price, review alerts (an `EQUITY_NOT_ENOUGH_BP` chip, not buried JSON), thesis with an unobtrusive marker when `thesis_source` is the fallback template, and the indicator readings; Approve/Reject with one confirmation step; decided/expired history with reasons. A `409` renders as "already \<status\>" and refreshes — it means the sweep or another surface won the race, which is the system working.
2. **Dashboard** — open lots, unrealized PnL when quotes are available, entry-basis when not; totals. No invented realized number.
3. **Controls** — kill switch, prominent, one confirmation, state read back from the server; mode toggle rendered locked while `live_trading_enabled` is false.
4. **Paper/live indicator** — a persistent banner at the app-shell level, on every screen, driven by `/v1/settings`. PRD §4.3 calls it unmistakable; a per-screen badge is how it gets forgotten.

## Milestones

**Exit: the owner approves or rejects real proposals on their phone; the CLI leaves daily use.**

- [x] 2.1 **Contract first.** ~~Write the real `docs/openapi.yaml`~~ — inverted per the note below: `docs/openapi.yaml` is now *generated* from the zod route schemas (`npm run openapi:write`) and checked in, with the drift test asserting the two agree. Fastify server with bearer auth and `/healthz` parity; spec-drift test green. Exit met: emitted spec matches the checked-in contract; authenticated `curl` lists pending signals; no/wrong token gets `401`; `/healthz` stays public.

  **Deviation from decision 3.** Hand-authoring the YAML and diffing it against the emitted spec fails on key order and `$ref` naming rather than on real drift, and a test that cries wolf gets muted. Generating it keeps one authoring surface (zod), keeps the checked-in contract the Swift generator consumes, and makes the drift test meaningful — verified by confirming it fails on a stale file. Unreferenced `*Input` schema variants are pruned so the generated Swift client does not carry dead types.

  **Also in 2.1:** zod upgraded 3.25 → 4.4. `fastify-type-provider-zod@5+` infers against zod v4 schema types, so on zod 3 every route silently lost its inferred request/response types. The alternative — pinning an old provider or running two zod dialects in one repo — was worse. All 173 pre-existing tests pass unchanged; the only source edits were `bool.default(false)` (v4 defaults take the output value) and tightening `HealthReport.executionMode` to the `ExecMode` enum.
- [x] 2.2 **Signals + decision endpoints.** `GET /v1/signals/{id}` and `POST /v1/signals/{id}/decision`. All listed integration tests green, plus kill-switch-blocks-approve and reject-still-allowed-while-halted. Exit met: full decide flow via `curl` (approve → paper fill at 182.6825 = estimate + 10bps slippage), and the CLI produced an identical fill on an equivalent signal.

  **Gates are pre-flighted before the transition, not after.** The immutability triggers only permit `pending → terminal`, so an approval the executor then refuses would strand a signal marked approved with no fill and no way back. Checking the kill switch and live-mode gates first means those refusals return `409` with the signal still pending and still decidable. The executor re-checks both and remains the authority; the residual window (switch flipped between check and fill) returns `500` with an explicit "approved but not filled" detail rather than a bare error the app would render as "retry".

  **Fixed en route:** `scripts/write-test-signal.ts` fabricated a review snapshot predating `ReviewSnapshotSchema`, so approving a test signal always failed to fill — the script's own `--decide approve` path included. It now writes a schema-valid snapshot. Found by the new error path reporting it honestly instead of 500-ing blankly.
- [x] 2.3 **Dashboard + settings endpoints.** `GET /v1/dashboard`, `GET`/`PUT /v1/settings`. Both listed tests green, plus partial-quote totals, sell-side PnL, and the empty-portfolio case. Exit met: kill switch flipped through the API halted the next pipeline run with `broker.calls` empty, and live mode returned `409` while `LIVE_TRADING_ENABLED` is false.

  **Quotes degradation was verified for real, not just mocked** — the local environment has no Robinhood credentials, so `getQuotes` genuinely failed and the endpoint returned all open lots on entry basis with `quotes_available: false` and totals withheld.

  **Two decisions worth knowing.** `listOpenLots` takes the latest track-record row per signal and *then* filters for open, rather than `WHERE status = 'open'` — the other order resurrects a position Phase 3 later closed. And a total is null unless every lot is quoted: a partial sum understates the portfolio, which is worse than admitting the number is unavailable.

  **Decimal-string convention, now documented in the spec:** stored prices serialize verbatim (`"100"`, not `"100.00"`), because padding them would mean rounding a four-decimal fill like `182.6825`. Computed aggregates are fixed at two places. The client formats for display.
- [~] 2.4 **Devices + APNs.** Everything buildable without an Apple account is done: `devices` migration, repository, `POST /v1/devices`, the hand-rolled APNs client over `node:http2`, and the pipeline hook. 22 tests, including the client driven against a real local HTTP/2 server. **Second half of the exit is blocked on the $99 Apple Developer Program** (risk 1) — a sandbox push landing on a real device cannot be demonstrated without it, and the app cannot register for remote notifications without the Push Notifications capability.

  Verified: push failure demonstrably does not block signal persistence. That test found a real bug — the hook sat inside the block that rethrows non-duplicate errors, so a throwing notifier would have aborted the whole run and cost the owner every remaining candidate. The notifier swallowing its own errors was not enough; the pipeline now guards the call itself.

  Also pinned: a token is pruned on 410 **and** on 400 `BadDeviceToken` (Apple uses 400 for a token that was never valid; pruning only on 410 leaves dead rows forever), a 503 does not prune, and one provider token is reused across pushes rather than minted per push, which Apple rejects as `TooManyProviderTokenUpdates` under load.
- [x] 2.5 **iOS scaffold.** XcodeGen project, generated OpenAPI client, Keychain-stored token, tab shell with the paper/live rail. Exit met: the app on the simulator lists real pending signals from the local backend.

  The contract is symlinked, not copied — `ios/Ollie/Networking/openapi.yaml` points at `docs/openapi.yaml`, which the generator explicitly supports and which keeps one source of truth. A backend route change now breaks the app at compile time.

  **Two contract bugs surfaced only by building the client.** `swift-openapi-generator` silently dropped every nullable property, so the degraded dashboard was unreadable (see the 3.0 conversion in `src/server/openapi.ts`); and the client needed `iso8601WithFractionalSeconds`, because the backend's `toISOString()` timestamps all carry milliseconds and strict ISO8601 rejected the entire response.

- [x] 2.6 **Approvals UI** end to end against local backend: list, detail, approve/reject, countdown, error states. Exit met: a signal approved by tapping in the simulator produced a paper fill in Postgres at `182.6825` — the estimate plus 10bps of slippage — with a null broker order id and an open track-record lot. Driven by an XCUITest, so it is repeatable rather than a one-off.

- [~] 2.7 **Dashboard + controls UI; device E2E.** The app half is done: Positions renders open lots with unrealized PnL and the degraded entry-basis state; Controls carries the kill switch behind one confirmation and the mode toggle visibly locked. Verified against a genuine broker failure — the dev machine has no Robinhood credentials, so the dashboard really did fall back and withhold its totals.

  **The device E2E is blocked**, on the Apple Developer Program (push on a real device) and on 1.7 (the Railway deploy and real credentials). Everything that does not need either is done and verified locally.

## Verification

1. **API integration tests** (vitest + local PG, mock broker): every row in the milestone list above; auth on every route; the spec-drift test.
2. **Concurrency:** decision racing the expiry sweep, decision racing a second decision — DB triggers already make the wrong outcome impossible; tests prove the API reports it correctly (`409`, current status, no duplicate execution row).
3. **Push:** dispatcher unit-tested against a fake HTTP/2 server (status-code handling, 410 pruning, JWT refresh under the 1-hour cap); one manual sandbox push per device class.
4. **App:** manual script per screen against seeded states — pending, decided, expired, alerts present, fallback thesis, broker-down dashboard, kill switch on. UI test automation is not a Phase 2 deliverable; the surface is four screens and one user.
5. **Safety regression:** `grep` still shows no `place_equity_order` call site; the API introduces none.

## Risks / open questions

1. **Apple Developer Program membership ($99/yr) is required for push.** Free provisioning cannot use APNs and its profiles expire weekly. Without it, milestones 2.4 and the push half of 2.7 are blocked; the app still works by foreground refresh, but a 15-minute expiry window with no push is a product defect, not a workaround. Buy it before 2.4.
2. **Owner-token auth is PRD drift** (decision 1). If declined, 2.1 grows SIWA verification (JWKS fetch, `apple_user_id` pinning) and the `users` table moves into this phase; everything downstream shifts accordingly.
3. **Executor runs synchronously inside the decision request.** Paper fills are milliseconds, so fine for Phase 2 — but the Phase 5 live path (fresh review + broker order) inside an HTTP handler would be wrong. Note for Phase 5: the decision endpoint returns `202` + a poll, or the executor moves behind a queue. The seam exists; don't solve it now.
4. **Quotes for unrealized PnL come from the broker adapter,** which couples the dashboard to broker auth health. Degradation to entry-basis is designed in; the risk is the owner reading a stale-quote PnL as current. Timestamp the quotes in the response and show their age.
5. **`expires_at` is computed from current config,** so changing `SIGNAL_EXPIRY_MINUTES` shifts the displayed countdown for signals already pending. The sweep has the same behavior today; acceptable for one owner, documented here.
6. **XcodeGen and swift-openapi-generator are new toolchain dependencies.** Both are actively maintained (Apple owns the second). If XcodeGen fights the project, the fallback is a checked-in `.xcodeproj` and hand-added files — worse for agent-driven work, not fatal.
7. **APNs token JWTs must be reused for 20–60 minutes** — minting per-push gets rejected as `TooManyProviderTokenUpdates`. The dispatcher caches the JWT with its issue time; this is the kind of detail the hand-rolled client must get right and the fake-server test pins down.
