# Ollie — Phase 4 Implementation Plan (subscriber side)

## Context

Phases 0–3 are code complete: the pipeline proposes and exits on schedule, the owner decides on the phone, marks accrue daily, and `GET /v1/track-record` computes the published numbers from append-only rows at read time. Production runs on Railway against the real Robinhood credential; the clean-slate record starts accruing Monday 2026-08-17 and Phase 3's sustained run exits after ~20 trading days with at least one closed trade. What nothing does yet is let anyone but the owner see any of it. `Signal.published` and `Signal.publishedAt` have existed since Phase 0 and **no line of `src/` reads or writes either** — that unwired seam is what this phase fills.

Phase 4 builds the subscriber side. **Exit (PRD §10): the Ollie Signal MCP server (read-only), subscriber onboarding, feed and track record view, disclaimer; soft launch to a small group.** The governing constraints come from PRD §4.5 and §9 and are not negotiable: the MCP server exposes no tool that can place, modify, or read any Robinhood order or account; an unauthenticated request returns nothing; Ollie never holds a subscriber credential and never trades on a subscriber's behalf; and every published number stays recomputable from the append-only rows, because that reproducibility *is* the credibility argument.

Phase 4 code can be built and verified entirely in parallel with the Phase 3 sustained run — nothing here touches signal generation, the decision flow, or the executor. Only the soft launch itself (4.7) waits on a record worth publishing.

## Decisions proposed here (owner should confirm before 4.1)

1. **A signal is published automatically when its approval's fill is recorded. No delay, no separate owner action, and never before the fill.**
   PRD §4.4 says "on owner approval," and in this codebase approval and fill are one synchronous sequence in the decision route — the paper executor fills in milliseconds inside the same request. Publishing *after* the execution row lands makes the ordering structural: a subscriber can never see a signal the owner's own book has not already filled, so front-running the owner is impossible by construction rather than by politeness. In paper mode the concern is theoretical anyway (a paper fill moves no real market and is priced from the review snapshot, not the tape), but building the ordering now means Phase 5's live flip inherits it instead of retrofitting it — the one place the ordering will actually matter. The alternatives all cost something real: publish-on-approval opens a fill-failure window where subscribers saw a signal the owner never held; a fixed delay staleness-taxes a daily-bar strategy for no owner benefit; owner-action publishing makes the feed's completeness depend on remembering a second tap, and a feed with silent holes is a curated record — exactly what §9 forbids. Rejected and expired signals are **not** published as signals (PRD §4.4 publishes approvals), but they are not hidden either: the track record's counts already reflect only approved trades, and the raw per-signal record a subscriber can walk contains every fill and mark behind each published claim. A crash between fill and flip is closed by a reconciliation sweep (4.1), so "approved with a fill but unpublished" is a state that lasts at most one sweep interval.

2. **The published flip is one-way, enforced in the database, not the application.**
   `signal-schema.md` already promises "a published signal cannot be unpublished." Today nothing enforces that; the immutability triggers on `signals` govern the status transition, not this column. The trigger migration in 4.1 extends them: `published` may change only `false → true` with `published_at` set exactly once in the same statement, and never back. An unpublishable-by-accident feed is table stakes for a product whose pitch is that the record cannot be edited.

3. **Subscribers get Sign in with Apple plus per-user hashed, revocable MCP tokens. The owner keeps the pre-shared token, unchanged.**
   Phase 2's deliberate drift (single `OWNER_API_TOKEN`, SIWA deferred "to Phase 4 where strangers make it earn its place") now comes due — for strangers only. Migrating the owner API to SIWA mid-record would churn the one surface that must not wobble (approvals, kill switch) for zero gain: the owner is one known person with a working Keychain-stored token and a break-glass CLI. So: subscribers sign in with Apple in the app (identity token verified against Apple's JWKS, `apple_user_id` is the identity), and after onboarding completes the app mints an opaque MCP token — shown in plaintext exactly once, stored as a sha256 hash (the same hash-then-compare doctrine as `auth.ts`), revocable by marking the row, per-user so one leak burns one subscriber. It differs from the owner's token in every way that matters: hashed at rest, many not one, revocable without a redeploy, accepted *only* by the signal service — the owner `/v1` surface rejects it, and the signal service rejects the owner token, because a credential that works on both sides of the owner/subscriber wall is a hole in the wall. The PRD's `subscriptions` table stays deferred again: no tier logic exists, monetization is gated on a lawyer (§9), and Phase 0's reasoning still holds — an unused table with a billing story attached is a liability.

4. **The subscriber surface is a second Railway service — same repo, same image, different entrypoint — with a database role that cannot read the broker credential.**
   The orchestrator process holds a live brokerage credential: `oauth_state` carries the rotating refresh token, and the environment carries its seed. The subscriber service is the only thing strangers touch. Those two facts must not describe the same process. Running the MCP server in-process with the orchestrator would put stranger-driven request parsing in the address space that holds the credential; a single deserialization bug away from the worst outcome this product has. The split is cheap and total: `src/signal-server/` gets its own entrypoint (`npm run start:signal`), deploys as a second Railway service from the same build, receives *none* of the `RH_*`/`ANTHROPIC_*`/`APNS_*`/`OWNER_API_TOKEN` variables, and connects to the same Postgres as a new `ollie_signal` role whose grants are explicit: `SELECT` on `signals` and `track_record`, read/write on the three subscriber tables (4.2), and **no privilege of any kind on `oauth_state`, `app_settings`, `devices`, `executions`, or `signal_events`** — so even a full compromise of the subscriber service cannot read the credential, flip the kill switch, or see the owner's fills. The costs are a second service's dollars and a second deploy to keep current, both acceptable; the same-image choice keeps the two from drifting apart in dependencies. Blast-radius bonus: subscriber load can never starve the pipeline cron. The subscriber REST API (onboarding, feed) lives in this same service, not the owner API — one stranger-facing surface, not two.

5. **The MCP surface is four read-only tools, and §4.5 is proven by tests that fail on any addition.**
   The full list, deliberately short (concrete signatures in the contract section): `list_signals`, `get_signal`, `get_track_record`, `get_disclaimer`. Deliberately absent: anything that writes, anything named order/account/position/watchlist/quote, anything broker-shaped at all — the server has no broker client to call even if a tool wanted one. The acceptance criterion needs a test that would fail if an order-capable tool were *ever* added, so 4.4 pins it three ways: (a) a surface snapshot test connects with the SDK client, lists tools, and asserts the exact sorted name array — any new tool fails CI until the snapshot is deliberately changed in review; (b) an import-graph test walks `src/signal-server/`'s dependencies and fails if anything under `orchestrator/robinhood/`, `orchestrator/executor`, or `orchestrator/push/` is reachable — the service *cannot* place an order because it cannot even construct the adapter whose only write method throws; (c) the `ollie_signal` role test proves the database would refuse the data such a tool would need. Unauthenticated requests are rejected at the HTTP layer with a bodyless 401 before any MCP handshake — no tool list, no error detail, nothing.

6. **The disclaimer is versioned text in the repo, shown full-screen before onboarding can complete, and acceptance is an append-only row keyed to the exact version accepted.**
   The text (drafted from PRD §9's required elements — not financial advice; past performance is not indicative of future results; you act at your own risk, through your own account, on your own agent's decisions; signals are generic and identical for every subscriber) lives at `docs/disclaimer.md`; its sha256 is the version. The onboarding screen requires scrolling to the end before Accept enables. Accepting writes a `disclaimer_acceptances` row — user, version hash, timestamp — under the same append-only triggers as the record, because "prove the subscriber saw it" is a claim about the past and this codebase already knows how to make those trustworthy. The MCP token mint *refuses* (`409`) unless a current-version acceptance row exists, which makes "saw it before onboarding completed" structural: the artifact onboarding produces cannot exist without the consent row predating it. A text change bumps the version and gates existing subscribers' *next* token mint on re-acceptance (existing tokens keep working — retroactively cutting off paid-nothing soft-launch users over a wording tweak is hostile; a lawyer-mandated change can revoke explicitly). The words themselves are a lawyer's to bless, not an engineer's — this milestone builds the plumbing and ships placeholder-quality text flagged as such in the risks.

7. **Subscribers see open positions at daily-mark granularity. No live unrealized PnL.**
   The owner's dashboard computes live unrealized PnL from broker quotes at read time. The subscriber surface gets no quotes because it has no broker path — that is decision 4, and piping quotes through the orchestrator to the signal service would re-couple the two processes precisely where they were separated. But the deeper reason stands on its own: a live number is transient and unreproducible, and everything this product publishes is supposed to be recomputable from the rows. The daily mark rows *are* the record's own answer to "what is the open position worth" — auditable (`mark_price` travels with each), append-only, and identical for every reader. So a subscriber sees an open position as: entry price, quantity, days held, and the latest mark with its date, clearly labeled as of the prior close. A subscriber who wants a live number has their own agent connected to their own market data — pricing the published entry themselves is a one-tool-call errand on their side of the wall.

8. **The soft launch is invite-gated: token mint additionally requires an invite code from `SUBSCRIBER_INVITE_CODES`, recorded on the user row.**
   "Small group" needs a mechanism, and env-configured codes are the cheapest one that leaves an audit trail (which code admitted whom). Open registration is a later config change — remove the gate, not rebuild the flow. An allowlist of emails fails against SIWA's private relay; codes do not care.

## Definitions (these become code and contract text verbatim)

- **A published signal** is the subset of the signal record defined by `signal-schema.md`'s Publication section, produced by one projection function (`toPublishedSignal`): `id`, `created_at`, `published_at`, `symbol`, `side`, `signal_type`, `quantity`, `thesis` (+ `thesis_source`), `indicators`, and the review snapshot's `estimated_price` only. What never crosses: `ref_id`, `review_snapshot.raw` (and `alerts` — the owner's account state), `execution_mode`, everything in `executions`, `decide_reason`, `dedupe_key`. Identical for every subscriber; no field varies by caller.
- **Publication** is the one-way `published=false → true` flip with `published_at` set once, after the approving fill's execution row exists.
- **A subscriber** is a `users` row with `role='subscriber'`, keyed by `apple_user_id`.
- **Onboarding is complete** when the user has a `disclaimer_acceptances` row for the current disclaimer version and at least one unrevoked MCP token. Both are checkable from rows; nothing about completion lives in app state.
- **The signal service** is the second deployable: subscriber REST plus the Ollie Signal MCP server, one process, `ollie_signal` database role, zero broker code in its import graph.
- **Per-signal record** = every `track_record` row for a published signal, verbatim (entry, marks with `mark_price`, close with `closed_by_signal_id`, corrections). This is the recompute path: a subscriber holding these rows can rerun the published aggregates and get the same numbers.

## Database changes

One migration for the subscriber tables, one for the trigger amendment and role. All monetary/identity conventions unchanged (uuid PKs, timestamptz, text over varchar).

```sql
CREATE TABLE users (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  role           text NOT NULL DEFAULT 'subscriber',      -- 'owner' | 'subscriber'; owner row unused until a later auth migration
  apple_user_id  text NOT NULL UNIQUE,                    -- the stable SIWA subject; THE identity
  email          text,                                    -- nullable: SIWA private relay may withhold or rotate it (PRD drift, argued in 4.2)
  invite_code    text,                                    -- which code admitted them; soft-launch audit trail
  created_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE subscriber_tokens (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      uuid NOT NULL REFERENCES users(id),
  kind         text NOT NULL,                             -- 'app' (REST session) | 'mcp' (agent-facing); neither surface accepts the other's
  token_hash   text NOT NULL UNIQUE,                      -- sha256 of the plaintext, which is shown once and never stored
  created_at   timestamptz NOT NULL DEFAULT now(),
  last_used_at timestamptz,
  revoked_at   timestamptz                                -- soft revoke: the row remains as history
);

CREATE TABLE disclaimer_acceptances (                     -- append-only, same trigger pattern as track_record
  id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id            uuid NOT NULL REFERENCES users(id),
  disclaimer_version text NOT NULL,                       -- sha256 of docs/disclaimer.md as served
  accepted_at        timestamptz NOT NULL DEFAULT now()
);
```

The trigger amendment: the `signals` update trigger additionally permits `published false→true` with `published_at` transitioning null→non-null in the same statement, and rejects any other change to either column (including on rows already published). `disclaimer_acceptances` gets the full append-only treatment: UPDATE, DELETE, and TRUNCATE all raise.

The role, in the same migration so no deploy can outrun it:

```sql
CREATE ROLE ollie_signal LOGIN;                           -- password set per-environment, never in the migration
GRANT SELECT ON signals, track_record TO ollie_signal;
GRANT SELECT, INSERT ON users, disclaimer_acceptances TO ollie_signal;
GRANT SELECT, INSERT, UPDATE ON subscriber_tokens TO ollie_signal;  -- UPDATE for revoked_at/last_used_at only
-- No grant of any kind on oauth_state, app_settings, devices, executions, signal_events.
```

`SELECT` on `signals` is broader than the published subset; the application filters `published = true` and projects through `toPublishedSignal`, and the redaction test — not a grant — is what proves the subset. A `published_signals` view was considered and rejected: it would be a second definition of the subset that can drift from the projection function the REST and MCP layers actually use.

Config additions: `SIGNAL_SERVICE_PORT`, `SIGNAL_DATABASE_URL` (the `ollie_signal` connection string), `PUBLISH_SWEEP_CRON=*/5 * * * *` (orchestrator side), `SUBSCRIBER_INVITE_CODES` (comma-separated), `APPLE_APP_BUNDLE_ID` (SIWA audience check).

## API contract summary

**Owner API (`docs/openapi.yaml`)** — one addition, no breaking change: signal summaries and detail gain `published` / `published_at`, so the owner app can render the published state. Regenerated as always; Swift client recompiles.

**Subscriber REST (`docs/openapi-subscriber.yaml`, new)** — served by the signal service, generated from its zod schemas with the same drift test, consumed by a second generator target in the iOS app. All under `/v1` on the signal service's own host; `/healthz` public.

- **`POST /v1/session`** — body: SIWA identity token (+ invite code on first sign-in). Verifies signature against Apple's JWKS, checks audience and expiry, upserts the `users` row by `apple_user_id`, mints an `app`-kind token (plaintext in the response, hash in the row). Wrong/missing invite code on a first sign-in → `403`. Everything below requires `Authorization: Bearer <app token>`.
- **`GET /v1/onboarding`** — current disclaimer version + text, whether this user has accepted it, whether an unrevoked MCP token exists. The app renders onboarding state from rows, not local flags.
- **`POST /v1/disclaimer/accept`** — body: the version hash the client displayed. Mismatch with current → `409` (the text changed under them; re-display). Writes the acceptance row.
- **`POST /v1/mcp-tokens`** — mints an `mcp`-kind token; response carries the plaintext (once) and the MCP URL. No current-version acceptance → `409 disclaimer_not_accepted`. This is the enforcement point for decision 6.
- **`GET /v1/mcp-tokens`** / **`DELETE /v1/mcp-tokens/{id}`** — list (created/last-used/revoked, never the plaintext) and revoke.
- **`GET /v1/feed?limit&before`** — published signals, newest first, `toPublishedSignal` projection, keyset-paginated on `published_at`.
- **`GET /v1/signals/{id}`** — one published signal plus its per-signal record rows. Unpublished or unknown id → the same `404`, indistinguishable on purpose.
- **`GET /v1/track-record`** — byte-for-byte the owner endpoint's shape (`TrackRecordSchema` is shared), plus `open_positions` detail per decision 7. Same `computeTrackRecord`, same rows, same numbers — the point.

**Ollie Signal MCP server** — Streamable HTTP at `/mcp` on the signal service, `Authorization: Bearer <mcp token>` required before the handshake; missing/unknown/revoked token → bodyless `401`, no session, no tool list. Server `instructions` carry the disclaimer and the one-line framing ("generic, non-personalized signals; your agent decides; nothing here can touch any brokerage account"). Tools, zod-schema'd:

- **`list_signals({ limit?: number ≤ 100, since?: ISO timestamp })`** → published signals, newest first, projection identical to the REST feed.
- **`get_signal({ id: uuid })`** → the published signal + per-signal record rows. Unpublished → not found.
- **`get_track_record({})`** → stats, curve (with `withheld` days), open positions at mark granularity.
- **`get_disclaimer({})`** → current disclaimer text + version. Exists so an agent can be told to check it; the same text is in `instructions` for agents that read those.

Nothing else. No resources with side effects, no sampling, no elicitation. Responses are identical for every authenticated caller — the token authenticates, it never personalizes.

## Milestones

**Exit: a small invited group receives published signals through their own agents via the MCP server, with recorded disclaimer acceptance, while the owner surface and broker credential remain unreachable from anything a subscriber touches.**

- [ ] 4.1 **The publishing seam.** Trigger amendment (one-way flip); `publishSignal` repo function; the decision route calls it after the execution row is written, with a publish failure logged and *not* failing the approval (the signal is filled and the sweep will catch it — same doctrine as push); `PUBLISH_SWEEP_CRON` reconciliation job publishing any approved signal that has an execution but `published=false`; `toPublishedSignal` with the redaction test asserting the forbidden fields are absent from its output for a fully-populated fixture signal; `signal-schema.md`'s Publication section updated from "will be" to "is", and the owner OpenAPI regenerated with the two new fields. **Exit:** approving a seeded signal locally sets `published_at` exactly once; a direct SQL attempt to unpublish or re-date it raises; a signal seeded approved-with-execution-but-unpublished is published by one sweep firing; the redaction test enumerates and passes.
- [ ] 4.2 **Identity, consent, and the wall.** The two migrations (tables, triggers, role); repo modules (`users`, `subscriberTokens`, `disclaimerAcceptances`) with mint/verify/revoke built on the `auth.ts` hashing primitive; a pure SIWA verifier module (JWKS fetch cached, signature/audience/expiry checks, fixture-tested against a locally-generated key pair — no network in tests); `docs/disclaimer.md` with its hash exposed as the version. DB tests: acceptances refuse UPDATE/DELETE/TRUNCATE; a connection as `ollie_signal` can read `signals` and `track_record`, can insert an acceptance, and gets a permission error on `SELECT` from each of the five denied tables — all five asserted individually, because this test *is* the §4.5 credential-isolation proof at the data tier. **Exit:** the role test names all five denials and passes; token mint round-trips (mint → verify plaintext → revoke → verify fails); the SIWA verifier rejects a tampered token and one with the wrong audience.
- [ ] 4.3 **The signal service and subscriber REST.** `src/signal-server/` entrypoint booting Fastify from `SIGNAL_DATABASE_URL`, refusing to start if the URL's role can read `oauth_state` (a boot-time probe, mirroring the owner API's refusal to boot tokenless); every route from the contract summary; `@fastify/rate-limit` per-token and per-IP; the second OpenAPI spec, drift test, and `npm run openapi:write` extension. Integration tests: the full onboarding sequence via `inject`; mint refused without acceptance; feed excludes unpublished signals; the owner token 401s here and an `app` token 401s on the owner API. **Exit:** against local PG via `curl`: session → onboarding → accept → mint → feed returns exactly the published fixture signals with forbidden fields absent; the `409 disclaimer_not_accepted` path demonstrated; both cross-surface token rejections demonstrated.

- [ ] 4.5 **Subscriber onboarding, iOS.** `Features/Subscriber/` scaffolded per the PRD layout; `RootView` branches: owner token in Keychain → owner tabs (unchanged), else the subscriber flow; SIWA via `ASAuthorizationAppleIDButton`; invite code entry; the disclaimer screen (scroll-to-end enables Accept); the token handoff screen — plaintext MCP token with copy button, the MCP URL, and setup steps for pointing an agent at it, plus the plain warning that the token is shown once; token list/revoke under settings. Second generator target consuming `openapi-subscriber.yaml` via the same symlink pattern. **Exit:** on the simulator against the local signal service, a complete onboarding run (sandbox SIWA → invite code → scroll/accept → token displayed) leaves the user, acceptance, and hashed token rows in Postgres, driven by an XCUITest like 2.6 so it is repeatable.
- [ ] 4.6 **Feed and track record, iOS subscriber side.** The feed (published signals, thesis, indicators, published-at timestamps); the subscriber track record screen reusing the Swift Charts curve and stats conventions from the owner's `TrackRecordView` — null win rate as "no closed trades yet", withheld days as visible gaps — plus open positions labeled "as of <mark date>" per decision 7; the disclaimer's one-line reminder persistent on both screens. **Exit:** the simulator renders feed and record for a seeded multi-trade fixture including the null-win-rate and withheld-gap states, and the numbers shown match the owner app's Track Record screen against the same database; XCUITest-driven.

## Verification

1. **Unit (no network/DB):** `toPublishedSignal` redaction (field-by-field, against a maximal fixture); SIWA verifier against locally-minted tokens (valid, tampered, expired, wrong audience); token hash round-trip; disclaimer version = file hash.
2. **DB tests:** one-way published flip (both illegal directions raise); acceptances append-only including TRUNCATE; the `ollie_signal` role's five denials and three grants, each asserted; revoked-token verification fails at the repo tier.
3. **Integration (local PG):** onboarding REST sequence; the sweep publishing a crash-window signal; MCP SDK client end to end — mint via REST, connect, call all four tools, revoke, next call 401s; feed/tool parity (same fixture, REST and MCP return identical projections); owner-vs-subscriber token cross-rejection.
4. **The §4.5 battery (4.4)** run as its own CI group, each test demonstrated to fail when its invariant is broken before being trusted green.
5. **Manual E2E (production):** the 4.7 rehearsal — fresh Apple ID, real device, external agent, production URL; confirm the acceptance row, the hashed token, and the tool round-trip in the service logs; confirm the signal-service Railway variables list contains no owner secret.
6. **Safety regression:** `grep` shows no `place_equity_order` call site anywhere new; the import-graph test holds; the orchestrator's own tests all still pass untouched — Phase 4 added consumers of the record, never writers.

## Risks / open questions

1. **Three items need a lawyer, not an engineer, before this phase's output is marketed or monetized:** the disclaimer wording (4.2 ships placeholder-quality text and says so), the marketing copy that keeps Ollie on the publisher side of the *Lowe*/publisher-exclusion line (PRD §9 — "connect your agent to a generic feed" is safe framing; anything resembling "auto-execute my picks" is not), and whether Robinhood's Agentic Trading terms permit redistributing MCP-derived data (the published `indicators` are computed from RH historicals) as a product. The soft launch stays free and invite-gated precisely to keep exposure low while these are open, per §9's "build phase carries no monetization exposure" — but "low" is not "zero," and the owner should get the disclaimer text reviewed before the first stranger accepts it.
2. **The launch gates on the record, and the record gates on the market.** 3.8 exits ~mid-September at the earliest, needs at least one closed trade, and "worth publishing" is a judgment call the plan already refused to reduce to a number. Everything through 4.6 builds and verifies now; if the record is thin when the code is done, the answer is waiting, and this plan says so rather than inviting scope-fill.
3. **SIWA on the client requires the paid Apple Developer capability and per-key service configuration.** The Phase 2 membership covers it, but Sign in with Apple has its own entitlement, key, and App ID configuration that has never been exercised in this project — budget a half-day of Apple-console friction in 4.5, and note that sandbox SIWA on the simulator has documented flakiness; the XCUITest may need a stubbed-verifier debug path like `TokenStore+Debug`.
4. **MCP client auth ergonomics are the real onboarding risk.** The server requires a static bearer header; MCP clients vary wildly in how (and whether) they let a user attach one — some only speak OAuth discovery. The Claude-family clients handle custom-header remote servers today, and the setup steps in 4.5 target them first; if the invited group's agents can't attach headers, the fix is an OAuth-shim milestone in a later phase, not a weaker auth default now. The rehearsal in 4.7 exists to find this before the invites do.
5. **The plaintext-once token will get lost.** Accepted: revoke-and-remint is two taps and the mint gate (current acceptance) is already satisfied for an existing subscriber. The alternative — recoverable tokens — means storing plaintext, which loses more than it saves.
6. **A correction row visibly reshapes the published curve at the correction date** (carried from Phase 3 risk 5, now due). The explanation surface is decision-by-construction: `get_signal` returns the raw rows, so the answer to "why did the curve change" is "the rows are public; recompute them" — the app and the MCP instructions should both say that sentence. What does not exist is a notification that a correction happened; subscribers discover it by looking. Acceptable for a soft launch, worth revisiting with real users.
7. **Publish-after-fill's front-running argument is paper-mode-strong and live-mode-untested.** Today the fill is synchronous and simulated, so the ordering is airtight. Phase 5's live fill may be slower, partial, or rejected after approval, and "publish when filled" needs re-deriving against real order states then — flagged here so the Phase 5 plan inherits the question instead of the assumption.
8. **Two services, one schema.** Migrations run from the orchestrator deploy; a signal-service deploy that outruns a migration it depends on will 500 until the orchestrator catches up. Same-repo/same-image keeps the window small, and the boot-time role probe catches the dangerous misconfiguration (wrong role) rather than the merely annoying one (missing table). Accepted for two services; revisit if there are ever three.
9. **Strangers on the internet, for the first time.** The attack surface is one bodyless-401 wall plus rate limits, and the credential isolation means the worst realistic outcome of a subscriber-service compromise is feed disclosure — signals that are published anyway — plus subscriber PII (`apple_user_id`s, relay emails, token hashes). That last set is real: it is the first personal data Ollie holds for anyone but the owner, and deleting a subscriber on request (relevant regulation aside, basic decency) collides with append-only acceptance rows. Proposed line: `users.email` is erasable operational data; acceptance rows are legal records and stay, keyed to an id whose email is gone. Worth thirty minutes of the same lawyer conversation as risk 1.
